# Ordin 實拿｜小店的外送利潤 agent

把兩個外送平台的對帳單、菜單成本丟給 agent，它算出每個品項在每個平台「每賣一份實拿多少」，找出賠錢的品項、活動、廣告與退款熱點，試算每個改法的影響，老闆勾選後產出一張照著改後台的變更清單。

> **全部資料都是模擬的。** 對帳單格式是依平台公開說明的費用項目自行設計，不是任何真實平台的匯出檔；店家、訂單、成本、需求彈性都由 `ordin/world.py` 產生。

## 一行啟動

```sh
python3 run.py
```

打開 <http://localhost:4103>。只需要 Python 3.10 以上，不用安裝任何套件，不需要 API key。

## Demo 操作步驟（約 2 分鐘）

1. 右上角店家選「小滿便當・平台 B 為新格式」（預設）。
2. 按 **▶ 回放 LLM agent**。左欄會一步步出現 agent 的動作：看檔案 → 對欄位並對帳 → 讀老闆備註 → 診斷 → 試算 → 交出清單。回放時 LLM 的決定是錄好的，畫面上每個數字都是現場重算的。
3. 右邊由上往下看：
   - 四個數字：外送營收、平台撥款、**實際留下**、新費率每月影響。
   - ① 對帳：兩種格式的欄位對應，逐筆重算撥款金額 100% 一致。
   - ② 營收排行 vs 實拿：營收第一名的品項是賠錢的。
   - ③ 每份實拿表：同一品項在內用、平台 A、平台 B 的差別；最右欄是「只扣抽成」的算法。
   - ④ 活動、廣告、退款。
   - ⑤ 建議動作：取消勾選任一項，總額與變更清單會即時重算。
   - ⑥ 變更清單與 agent 寫給老闆的說明。
4. 按 **決定性模式（不用 LLM）**：因為平台 B 是沒看過的表頭，內建欄位對應讀不了，會明確顯示失敗。把店家切到「標準格式」再按一次就會成功。這是用來說明 LLM 在這裡負責什麼。
5. 按右上角 **驗證**：30 家模擬店家的找出率、對照組、決策效果，以及 LLM agent 的端到端評測。
6. （選用）按 **即時 LLM**：現場呼叫模型，約 1 分鐘。有 `ANTHROPIC_API_KEY` 時走 Messages API，否則走本機已登入的 `claude` CLI。

## 其他指令

```sh
python3 run.py test                 # 13 個單元測試（手算小例子、對帳、端到端）
python3 run.py bench 30             # 30 家模擬店家的驗證，寫入 results/benchmark.{json,md}
python3 run.py llm-eval 1 2 3       # 用真的 LLM 跑指定種子的店家並評分，寫入 results/llm_eval.json
python3 run.py agent data/demo live # 在命令列跑一次 LLM agent
python3 run.py gen 42 data/shop42   # 產生一家新的模擬店家（第三個參數加 2 可讓平台 B 變成新格式）
```

環境變數：`ORDIN_LLM=api|cli|auto`（預設 auto）、`ORDIN_MODEL`（API 模型，預設 `claude-sonnet-5-5`）、`ORDIN_CLI_MODEL`（CLI 模型別名，預設 `sonnet`）、`PORT`（預設 4103）。

## 架構

```
老闆的檔案（data/<店家>/）
  A_orders.csv  A_items.csv  A_ads.csv      平台 A 對帳單（中文表頭，扣款為正數）
  B_orders.csv  B_items.csv  B_ads.csv      平台 B 對帳單（英文或新表頭，扣款為負數，日期格式不同）
  menu_costs.csv  platform_menu.csv  promos.csv  contract.json  pos_direct.csv
  owner_note.txt                             老闆用口語寫的限制
        │
        ▼
ordin/agent.py   agent 迴圈與工具：list_files / read_file / ingest / set_constraints /
                 analyze / price_options / simulate / finish
                 三種執行方式：live（LLM）、replay（錄製回放）、scripted（無 LLM）
        │  LLM 只輸出「要呼叫哪個工具、參數是什麼」
        ▼
ordin/core.py    所有金額的計算：
                 ingest()   依欄位對應讀檔 + 三項硬檢查（逐筆撥款金額、品項加總、佣金費率）
                 analyze()  每品項每平台的實拿、活動、廣告、退款
                 project()  給定一組動作，推估下個月留下多少
                 playbook() 規則版建議；validate_actions() 檢查老闆限制
ordin/world.py   模擬店家產生器 + 正解 + agent 看不到的隱藏參數
ordin/bench.py   驗證    ordin/llm_eval.py  LLM 端到端評測    ordin/server.py  本機伺服器
web/index.html   單頁介面
```

### LLM 做什麼、不做什麼

| LLM 負責 | 程式負責 |
|---|---|
| 判斷沒看過的對帳單每個欄位的意思 | 逐筆重算撥款金額，對不上就退回 |
| 把老闆的口語限制轉成結構化限制 | 檢查每個動作有沒有違反限制，違反就不能結束 |
| 決定要試算哪些改法、選哪一組動作 | 每個改法的金額試算 |
| 用老闆聽得懂的話寫說明 | 評測時檢查說明裡的金額是否都出現在工具輸出中 |

### 「實拿」的定義

每份實拿 ＝ 平台售價 − 佣金（含 5% 營業稅）− 店家負擔的折扣 − 退款 − 食材成本 − 包材 − 提袋餐具分攤。
這是邊際貢獻，**沒有扣人事與房租**。

### 影響試算的假設（寫在 `core.project()`）

- 需求是線性的：售價每漲 1%，該品項銷量掉 ε%。agent 一律假設 ε＝1.5；評分用的模擬器使用每個品項各自的真實 ε（主餐 0.8–1.8、配菜與湯 1.2–2.5、飲料 1.5–3.0），agent 看不到。
- 退出活動、停廣告：「因為活動才來」的訂單消失，其餘照原價留下。agent 假設一半；真實比例是隱藏的。
- 下架：一部分客人改點同類別最熱賣的品項（agent 假設 30%，真實 20–50%）。
- 換防漏包材：每份多 3 元，退款減少（agent 假設 70%，真實 50–90%）。
- **沒有模擬的事**：平台排序與曝光變化、外送客流回內用、競爭對手反應、整單因主餐漲價而流失。

## 驗證結果摘要（實際跑出來的數字，見 `results/`）

- 30 家模擬店家、203 個埋入的問題：系統找出率 100%、精確率 100%；「只看營收報表」26%；「只扣抽成」0%。
- 建議動作在隱藏參數的模擬器中，每家每月多留下平均 20,624 元（不動作時平均 17,922 元），30 家都有改善；三種彈性情境下為 20,301–20,983 元。
- 「全面漲到打平價」在基準情境平均 +20,876 元，低彈性時 +40,547 元（比本系統好），高彈性時只剩 +3,278 元且 37% 的店變差，並有 571 個動作超過老闆的漲價上限。
- LLM agent 端到端評測的數字見 `results/llm_eval.json` 與介面的「驗證」頁。

### 這些數字的限制

1. 正解的定義就是完整成本會計，所以「引擎找出率 100%」只證明程式算對了（另有 13 個單元測試與對帳恆等式佐證），不代表在真實店家上的表現。
2. 埋入的賠錢品項都是「食材成本高、平台沒加價」的類型，「只扣抽成」的算法看起來仍有賺，所以該對照組是 0%。這是出題方式的結果。
3. 每家店都埋了 5–9 個問題，改善金額反映的是埋了多少問題，不是市場估計。
4. 需求彈性是假設的，沒有真實資料校正。
